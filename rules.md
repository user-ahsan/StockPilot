This file defines the **150 non-negotiable engineering rules** for building and maintaining the **StockPilot** monolith. Every AI coding agent and human engineer must obey all 150 rules without exception.

## Section 4: Mental Model — What to Think Before & While Writing Code (Rules 046–060)

* **Rule 046:** Before writing a single line of code for any ticket, read `AGENTS.md`, `CLAUDE.md`, `rules.md`, and the corresponding section of Documents 1–6.
* **Rule 047:** Ask yourself Question 1 before coding any feature: *"Does this action mutate inventory, prices, or order state, and if so, what is its exact ACID transaction boundary?"*
* **Rule 048:** Ask yourself Question 2 before coding any endpoint: *"What happens if two warehouse clerks or two sales associates click this button at the exact same millisecond?"*
* **Rule 049:** Ask yourself Question 3 before coding any mutation: *"What happens if the warehouse Wi-Fi drops after the database commits but before the HTTP response reaches the browser, and the client retries?"*
* **Rule 050:** Ask yourself Question 4 before coding any route: *"Which of the 6 RBAC roles (`OWNER`, `MANAGER`, `PROCUREMENT_OFFICER`, `WAREHOUSE_CLERK`, `SALES_ASSOCIATE`, `AUDITOR`) are permitted to execute this, and is `organization_id` enforced on every query?"*
* **Rule 051:** Ask yourself Question 5 before coding any UI component: *"Am I using only CLI-installed Shadcn components and `caffeine` semantic tokens without touching any config or CSS file?"*
* **Rule 052:** Think in **State Machines**, not boolean flags: verify valid state transitions (`DRAFT -> SUBMITTED -> APPROVED -> ORDERED -> PARTIALLY_RECEIVED -> RECEIVED`) and reject illegal jumps (`DRAFT -> RECEIVED`).
* **Rule 053:** Think in **Append-Only Ledgers**, not destructive overwrites: every change in stock or order status is a historical event that must leave an immutable trail.
* **Rule 054:** Think in **Minor Currency Units (Integer Cents)**: always trace how prices, costs, taxes, discounts, and valuations multiply and sum without ever producing a decimal float.
* **Rule 055:** Think in **Multi-Tenant Isolation**: every `SELECT`, `UPDATE`, and `INSERT` must explicitly filter by `organization_id` derived from the verified server session—never from client request bodies.
* **Rule 056:** Think in **Deterministic Lock Ordering**: whenever locking multiple rows (`purchase_order_items`, `sales_order_items`, `inventory_balances`), always sort target IDs in ascending order first so two transactions can never deadlock each other.
* **Rule 057:** Think in **Graceful Conflict Recovery**: when a `409 Conflict` occurs (concurrent receipt or insufficient stock), return the exact current database state in the error payload so the frontend can immediately reconcile the UI for the user.
* **Rule 058:** Verify that every new file path matches the monolithic file tree in Document 2 before creating it.
* **Rule 059:** Write small, pure, single-responsibility functions (< 60 lines per function) with explicit parameter and return types.
* **Rule 060:** Never leave `TODO`, `FIXME`, mock data arrays, or stubbed placeholder functions in completed tickets; every ticket must deliver production-complete logic.

## Section 5: Inventory Ledger Invariants & Zero Blind Stock Overrides (Rules 061–075)

* **Rule 061:** NEVER allow the frontend to set or overwrite `on_hand_qty`, `reserved_qty`, or `available_qty` via a product edit form or catalog PATCH endpoint.
* **Rule 062:** The `PATCH /api/v1/products/[variantId]` Zod schema must use `.strict()` and explicitly reject any payload containing quantity fields with `400 Bad Request`.
* **Rule 063:** `src/server/services/inventory-ledger.service.ts` (`InventoryLedgerService`) is the **only** module in the entire codebase permitted to execute `INSERT INTO stock_movements` or `UPDATE inventory_balances`.
* **Rule 064:** Every call to `InventoryLedgerService.applyMovement()` MUST execute inside an active PostgreSQL transaction (`tx`) passed by the calling domain service.
* **Rule 065:** Every `stock_movements` record must store `balance_before`, `quantity_delta` (`!= 0`), and `balance_after`, where `balance_after === balance_before + quantity_delta`.
* **Rule 066:** For any `(organization_id, location_id, product_variant_id)`, the invariant `SUM(stock_movements.quantity_delta) === inventory_balances.on_hand_qty` must hold true at all times.
* **Rule 067:** `available_qty` must always equal `on_hand_qty - reserved_qty` (enforced via PostgreSQL `GENERATED ALWAYS AS (on_hand_qty - reserved_qty) STORED`).
* **Rule 068:** `on_hand_qty` must never drop below `0` (`CHECK (on_hand_qty >= 0)`).
* **Rule 069:** `reserved_qty` must never drop below `0` (`CHECK (reserved_qty >= 0)`).
* **Rule 070:** `on_hand_qty` must never be less than `reserved_qty` (`CHECK (on_hand_qty >= reserved_qty)`), guaranteeing `available_qty >= 0` at the storage engine level.
* **Rule 071:** Every `stock_movements` row must link to its causal business transaction via `reference_type` (`'PURCHASE_ORDER'`, `'SALES_ORDER'`, `'STOCK_ADJUSTMENT'`, `'TRANSFER'`) and `reference_id` (`UUID`).
* **Rule 072:** Confirming a Sales Order (`DRAFT -> CONFIRMED`) increments `reserved_qty` without changing `on_hand_qty` and logs a reservation audit record.
* **Rule 073:** Fulfilling a Sales Order (`CONFIRMED -> FULFILLED`) atomically decrements both `reserved_qty` and `on_hand_qty` and appends a `SALE_FULFILLMENT` movement (`-qty`).
* **Rule 074:** Canceling a `CONFIRMED` Sales Order atomically decrements `reserved_qty`, restoring `available_qty`.
* **Rule 075:** Receiving a Purchase Order increments `on_hand_qty`, appends a `PO_RECEIPT` movement (`+qty`), increments `purchase_order_items.received_qty`, and updates the PO status to `PARTIALLY_RECEIVED` or `RECEIVED`.

## Section 6: Pessimistic Concurrency Control, Row Locking & Deadlock Prevention (Rules 076–090)

* **Rule 076:** Always acquire a pessimistic row lock (`SELECT ... FOR UPDATE`) on the parent `purchase_orders` row before processing any stock receipt for that PO.
* **Rule 077:** Always acquire `SELECT ... FOR UPDATE` on all targeted `purchase_order_items` rows sorted by `product_variant_id ASC`.
* **Rule 078:** Inside the lock, verify `item.received_qty + incoming_qty <= item.ordered_qty` for every line item; if any line item exceeds `ordered_qty`, roll back the entire transaction and return `409 Conflict`.
* **Rule 079:** Always acquire `SELECT ... FOR UPDATE` on all targeted `inventory_balances` rows sorted by `(location_id, product_variant_id) ASC` via `src/server/db/locks.ts`.
* **Rule 080:** If an `inventory_balances` row does not yet exist for a `(organization_id, location_id, product_variant_id)` during first receipt, execute `INSERT ... ON CONFLICT (organization_id, location_id, product_variant_id) DO NOTHING` before selecting `FOR UPDATE`.
* **Rule 081:** During Sales Order confirmation, lock all requested `inventory_balances` rows in `product_variant_id ASC` order and verify `available_qty >= requested_qty` for every item before reserving any stock.
* **Rule 082:** If even one line item on a Sales Order lacks sufficient `available_qty`, roll back the entire reservation transaction and return a structured `409 Conflict` listing the exact SKU, requested quantity, and currently available quantity.
* **Rule 083:** Increment `inventory_balances.version` (`version = version + 1`) and update `last_movement_id` and `updated_at = NOW()` on every balance mutation.
* **Rule 084:** Never perform external HTTP requests (such as sending supplier emails via Resend or calling webhooks) while holding an open database transaction or `FOR UPDATE` row lock.
* **Rule 085:** Instead of making external network calls inside transactions, insert an event row into `automation_outbox_events` inside the same database transaction and commit immediately.
* **Rule 086:** Set `statement_timeout = '10s'` and `lock_timeout = '5s'` on transactional connections so a stalled query never blocks warehouse operations indefinitely.
* **Rule 087:** In the outbox worker (`/api/internal/cron/outbox-processor`), always use `SELECT ... FOR UPDATE SKIP LOCKED` so concurrent worker invocations never process the same outbox event twice.
* **Rule 088:** Enforce `UNIQUE(purchase_order_id, product_variant_id)` on `purchase_order_items` and `UNIQUE(sales_order_id, product_variant_id)` on `sales_order_items` so the same SKU cannot appear on two separate lines of the same order.
* **Rule 089:** Enforce `ON DELETE RESTRICT` on all foreign keys referencing `organizations`, `locations`, `suppliers`, `products`, `product_variants`, and `members` from transactional tables so historical records can never be orphaned or cascade-deleted.
* **Rule 090:** Use soft deactivation (`is_active = false` or `is_archived = true`) instead of `DELETE` for products, variants, suppliers, locations, and staff members.

## Section 7: Network Fluctuations, Idempotency & Adaptive Polling (Rules 091–105)

* **Rule 091:** Every state-mutating API endpoint (`POST`, `PATCH`, `PUT` on POs, SOs, Adjustments, CSV Commits) must be wrapped in `withIdempotency` middleware requiring an `Idempotency-Key` HTTP header.
* **Rule 092:** Reject any mutating request missing a valid `Idempotency-Key` header (min 16, max 128 chars) with `400 Bad Request`.
* **Rule 093:** Compute a SHA-256 hash of `(organization_id, member_id, method, path, rawRequestBody)` for every idempotent request and store it in `idempotency_keys.request_hash`.
* **Rule 094:** When an `Idempotency-Key` already exists with status `COMPLETED` and a matching `request_hash`, immediately return the stored `response_status` and `response_body` with header `X-Idempotency-Replayed: true` without touching business tables.
* **Rule 095:** When an `Idempotency-Key` already exists with a *different* `request_hash`, reject the request with `422 Unprocessable Entity (Idempotency key reused with different request payload)`.
* **Rule 096:** When a duplicate request arrives while the first request with the same `Idempotency-Key` is still `IN_PROGRESS` (and `locked_until > NOW()`), return `409 Conflict` with `Retry-After: 2`.
* **Rule 097:** On the frontend, `useIdempotentMutation` must generate a deterministic UUID `Idempotency-Key` when a form or action intent is initialized and **preserve that exact key across network errors, timeouts, and retry clicks**.
* **Rule 098:** Rotate the client `Idempotency-Key` only after receiving a definitive `2xx` success, a `400/422` validation failure requiring payload edits, or an explicit form reset by the user.
* **Rule 099:** Disable mutation submit buttons while a request is in flight (`isPending === true`) to prevent accidental double-clicks on laggy warehouse touchscreens.
* **Rule 100:** Wrap all frontend `fetch` calls in `src/lib/api-client.ts` with an `AbortController` timeout driven by `NEXT_PUBLIC_REQUEST_TIMEOUT_MS`.
* **Rule 101:** Implement frontend-to-backend synchronization via the lightweight cursor endpoint `GET /api/v1/sync/poll?locationId=...&sinceLedgerId=...` rather than polling heavy full-table endpoints every few seconds.
* **Rule 102:** Only invalidate TanStack Query caches (`['overview']`, `['products']`, `['purchase-orders']`, `['inventory-balances']`) when `/api/v1/sync/poll` reports a newer `latestLedgerId` or `latestPoUpdatedAt` than the client's cached cursor.
* **Rule 103:** Configure `useAdaptivePolling` to poll at `NEXT_PUBLIC_POLLING_ACTIVE_MS` (`5000ms`) on active operational screens and `NEXT_PUBLIC_POLLING_IDLE_MS` (`15000ms`) on catalog/report screens.
* **Rule 104:** Automatically pause polling when `document.visibilityState === 'hidden'` (`refetchIntervalInBackground: false`) and trigger an immediate delta sync when the tab regains focus.
* **Rule 105:** On network poll failure, apply exponential backoff with full jitter (`min(60000, base * 2^attempt) + random(0, 1000)ms`) and transition `<PollingStatusBadge />` to the degraded connection warning state after 2 consecutive failures.

## Section 8: Monetary Precision, Explicit Currency & Safe CSV Processing (Rules 106–120)

* **Rule 106:** Store all monetary values (`unit_cost_cents`, `selling_price_cents`, `subtotal_cents`, `tax_cents`, `shipping_cents`, `discount_cents`, `total_cents`) as PostgreSQL `BIGINT` minor units (integer cents).
* **Rule 107:** Never use `FLOAT`, `REAL`, `DOUBLE PRECISION`, or JavaScript decimal floating-point math (`0.1 + 0.2`) for currency calculations.
* **Rule 108:** Pair every monetary column in the database and every monetary field in API responses with an explicit 3-letter ISO 4217 `currency` code (`'USD'`, `'EUR'`, `'GBP'`, `'PKR'`).
* **Rule 109:** Validate in both Zod and PostgreSQL (`CHECK`) that line-item currencies match their parent Purchase Order or Sales Order currency.
* **Rule 110:** Snapshot `unit_cost_snapshot_cents` on `sales_order_items` and `stock_adjustments` at the exact moment of the transaction so historical COGS and shrinkage reports never shift if a product's cost is edited months later.
* **Rule 111:** Format all UI monetary outputs through `formatMoney(amountCents, currency)` from `src/lib/money.ts`.
* **Rule 112:** On Sales Order creation, ignore any client-supplied selling price and read `selling_price_cents` directly from `product_variants` inside the database transaction unless a verified `OWNER`/`MANAGER` discount override is applied.
* **Rule 113:** Enforce a two-step Bulk CSV Import architecture: Step 1 (`POST /api/v1/products/import/validate`) performs a side-effect-free dry run; Step 2 (`POST /api/v1/products/import/commit`) commits validated rows idempotently.
* **Rule 114:** Block CSV Formula Injection (CSV Macro Injection): reject or sanitize any CSV cell whose trimmed value begins with `=`, `+`, `-`, `@`, `\t`, or `\r`.
* **Rule 115:** Enforce a strict `10 MB` file size cap and `10,000` row maximum per CSV upload request.
* **Rule 116:** Detect duplicate `sku` values *within* the uploaded CSV file itself during the validation preview and flag them as row-level errors before hitting the database.
* **Rule 117:** Never allow a single malformed CSV row to crash the parser or abort valid rows silently; return a structured `{ validRows[], invalidRows[], summary }` preview showing exact row numbers, column names, and error descriptions.
* **Rule 118:** Allow the user in the CSV Import UI to download a CSV of rejected rows with an appended `error_reason` column and commit the valid rows safely in a single batch transaction.
* **Rule 119:** Escape all string fields during CSV export (`GET /api/v1/products/export`) to prevent formula execution in spreadsheet software.
* **Rule 120:** Record an `AUDIT_BULK_CATALOG_IMPORT` entry in `audit_logs` detailing total uploaded rows, imported valid rows, and rejected row counts.

## Section 9: Security, RBAC, Secret Isolation & Forensic Audit Logging (Rules 121–135)

* **Rule 121:** Place `import 'server-only';` at the top of every file in `src/server/**` so Next.js fails the build immediately if server code or secrets are imported by a client component.
* **Rule 122:** Never prefix sensitive secrets (`DATABASE_URL`, `DIRECT_DATABASE_URL`, `SESSION_JWT_SECRET`, `CRON_SHARED_SECRET`, `EMAIL_PROVIDER_API_KEY`, `SUPPLIER_WEBHOOK_SIGNING_SECRET`) with `NEXT_PUBLIC_`.
* **Rule 123:** Hash all user passwords using Argon2id; never log plaintext passwords, session cookies, or JWT tokens.
* **Rule 124:** Store session tokens exclusively in `HttpOnly; Secure; SameSite=Lax` cookies; never store JWTs in `localStorage` or `sessionStorage`.
* **Rule 125:** Enforce `withAuth` and `withRbac` on every `/api/v1/**` route handler; never rely on hiding a button in the React UI as a security control.
* **Rule 126:** Enforce Separation of Duties on Purchase Orders: a `PROCUREMENT_OFFICER` can draft and submit a PO (`DRAFT -> SUBMITTED`), but only a `MANAGER` or `OWNER` can approve and authorize it (`SUBMITTED -> ORDERED`).
* **Rule 127:** Restrict `unit_cost_cents` and `selling_price_cents` modifications exclusively to `OWNER` and `MANAGER` roles; log any unauthorized attempt to `audit_logs` and return `403 Forbidden`.
* **Rule 128:** Restrict physical PO stock receipt (`POST /api/v1/purchase-orders/[poId]/receive`) to `WAREHOUSE_CLERK`, `MANAGER`, and `OWNER` roles.
* **Rule 129:** Restrict Sales Order creation and fulfillment to `SALES_ASSOCIATE`, `MANAGER`, and `OWNER` roles.
* **Rule 130:** Enforce strict read-only access for the `AUDITOR` role across all endpoints (`GET` allowed, all `POST`/`PATCH`/`PUT`/`DELETE` blocked with `403 Forbidden`).
* **Rule 131:** Require a valid `reason_code` enum and a detailed human explanation (`reason_notes` >= 15 characters) on every Stock Adjustment submission, capturing `actor_member_id` from the authenticated session.
* **Rule 132:** Automatically flag any Stock Adjustment as `is_suspicious = true` if `ABS(quantity_delta * unit_cost_cents) >= SUSPICIOUS_ADJ_VALUE_CENTS` ($500.00), `ABS(quantity_delta) > 10%` of current `on_hand_qty`, or the actor has submitted >= 3 negative adjustments within 24 hours.
* **Rule 133:** Write an immutable `audit_logs` record inside the same database transaction for every PO state transition, stock receipt, sales order confirmation/fulfillment, stock adjustment, price change, and RBAC violation.
* **Rule 134:** Maintain the PostgreSQL `BEFORE UPDATE OR DELETE` immutability trigger on both `stock_movements` and `audit_logs` so historical records can never be altered or erased.
* **Rule 135:** Protect internal automation cron endpoints (`/api/internal/cron/*`) with constant-time HMAC/Bearer verification against `CRON_SHARED_SECRET`.
