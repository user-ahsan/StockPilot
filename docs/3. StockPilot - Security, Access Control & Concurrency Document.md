# **3\. StockPilot — Security, Access Control & Concurrency Document**

# **3.1 Authentication, Password Storage & Token Lifecycle**

* **Password Hashing Standard:**  
  * All user passwords are hashed using **Argon2id** (`memoryCost: 65536` (64 MB), `timeCost: 3`, `parallelism: 4`, 16-byte cryptographic random salt). Plaintext passwords are never logged, cached, or stored in memory beyond request validation.  
* **Token Architecture & Session Storage:**  
  * **Access Tokens:** Short-lived (15-minute expiry) signed JWT (`HS256` or `EdDSA`) stored exclusively in an `HttpOnly; Secure; SameSite=Lax; Path=/` cookie (`sp_access_token`). Never stored in `localStorage` or `sessionStorage`, eliminating XSS token theft.  
  * **Refresh Tokens:** 7-day rotating opaque tokens stored in an `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth/refresh` cookie (`sp_refresh_token`), backed by a hashed record in the `user_sessions` table with `family_id`.  
  * **Refresh Token Reuse Detection:** If a previously rotated refresh token is presented again (indicating token compromise or replay), the server immediately revokes the entire token `family_id` and forces re-authentication across all devices for that user.  
  * **Immediate Role/Revocation Enforcement:** Every state-mutating request verifies the user's current `role` and `is_active` status from a fast indexed lookup (or 30-second cache invalidated on member update) so demoted or deactivated staff lose write access immediately without waiting for JWT expiry.

# **3.2 Strict API Key & Secret Isolation Rules**

* **Compile-Time Boundary Enforcement (`server-only`):**  
  * Every file inside `src/server/**` and `src/lib/env.ts` (server section) imports `'server-only'` at line 1\. Any accidental import of a server module, database credential, or third-party API key into a Client Component causes an immediate Next.js build error.  
* **`NEXT_PUBLIC_*` Allowlist Rule:**  
  * Only non-sensitive configuration (`NEXT_PUBLIC_APP_ENV`, `NEXT_PUBLIC_APP_URL`, polling intervals, and timeout constants) may use the `NEXT_PUBLIC_` prefix.  
  * Database connection strings (`DATABASE_URL`, `DIRECT_DATABASE_URL`), JWT signing secrets (`SESSION_JWT_SECRET`), supplier webhook secrets, and email API keys are strictly server-only environment variables read exclusively inside Route Handlers and Server Services.  
* **CI/CD Secret Scanning & Git Hygiene:**  
  * `.env.local`, `.env.development.local`, and `.env.production` are strictly `.gitignore`d. Pre-commit hooks run secret regex scanners to block accidental commits of keys or tokens.

# **3.3 Role-Based Access Control (RBAC) & Prevention of Unauthorized Price/Quantity Changes**

* **Fundamental Security Invariant — No Direct Quantity Edits:**  
  * The product catalog editing endpoint (`PATCH /api/v1/products/[variantId]`) **does not accept** `on_hand_qty`, `reserved_qty`, or `available_qty` in its Zod schema (`.strict()`). Any request attempting to pass stock quantity fields to a metadata endpoint is rejected with `400 Bad Request (Unrecognized key: on_hand_qty — Stock balances can only be mutated via ledger transactions)`.  
* **Prevention of Unauthorized Cost & Selling Price Changes:**  
  * Updating `unit_cost_cents` or `selling_price_cents` requires `OWNER` or `MANAGER` role permissions.  
  * If a `PROCUREMENT_OFFICER`, `WAREHOUSE_CLERK`, or `SALES_ASSOCIATE` calls `PATCH /api/v1/products/[variantId]` with altered price fields, `withRbac(['OWNER', 'MANAGER'])` intercepts the request and returns `403 Forbidden` while writing an `AUDIT_UNAUTHORIZED_PRICE_CHANGE_ATTEMPT` event to `audit_logs`.  
  * On Sales Orders (`POST /api/v1/sales-orders`), the backend ignores any client-supplied unit price and always fetches the authoritative `selling_price_cents` directly from `product_variants` inside the database transaction, unless a Manager explicitly provides a signed discount override.

# **3.4 Concurrency, Race Conditions & Pessimistic Locking Protocols**

## **Scenario A: Two Staff Members Receiving Stock Concurrently**

* **Threat:** A Purchase Order has `10` units ordered and `0` received. Clerk A and Clerk B both open the Receive screen at the same time and both click "Receive 10 units" within 20 milliseconds of each other. Without row locking, both read `received_qty = 0`, both add `10`, and inventory is inflated to `20` units.  
* **Defense Mechanism (`purchase-order.service.ts`):**  
  * Open `db.transaction(async (tx) => { ... })`.  
  * Lock the parent PO row: `SELECT * FROM purchase_orders WHERE id = $poId AND organization_id = $orgId FOR UPDATE`.  
  * Verify PO status is `ORDERED` or `PARTIALLY_RECEIVED`. (When Clerk B's transaction acquires the lock 5ms after Clerk A commits, PO status is already `RECEIVED`—Clerk B's transaction immediately aborts with `409 Conflict`).  
  * Lock all targeted `purchase_order_items` sorted by `product_variant_id ASC` (`FOR UPDATE`).  
  * For each line item, assert `item.received_qty + incoming_qty <= item.ordered_qty`. If violated, `ROLLBACK` and return structured `409 Conflict` detailing exact remaining receivable quantity.  
  * Lock `inventory_balances` rows sorted by `(location_id, product_variant_id) ASC` (`FOR UPDATE`).  
  * Insert immutable `stock_movements` rows (`type = 'PO_RECEIPT'`, `quantity_delta = +incoming_qty`, `balance_after = current + incoming_qty`).  
  * Increment `inventory_balances.on_hand_qty` and `purchase_order_items.received_qty`, update PO status, write `audit_logs`, and `COMMIT`.

## **Scenario B: Concurrent Sales Associates Overselling Last Unit**

* **Threat:** Only `1` unit of *Ryzen 7 7800X3D* is available. Two Sales Associates submit Sales Orders for `1` unit at the exact same millisecond.  
* **Defense Mechanism (`sales-order.service.ts`):**  
  * Inside `db.transaction`, lock the requested `inventory_balances` rows in deterministic `product_variant_id ASC` order using `SELECT ... FOR UPDATE`.  
  * Re-compute `available_qty = on_hand_qty - reserved_qty` inside the lock.  
  * Assert `available_qty >= requested_qty` (additionally enforced by PostgreSQL `CHECK (on_hand_qty >= 0 AND reserved_qty >= 0 AND on_hand_qty >= reserved_qty)` constraint).  
  * Transaction 1 succeeds and increments `reserved_qty = 1`. Transaction 2 unblocks, sees `available_qty = 0`, rolls back cleanly, and returns `409 Conflict: Insufficient Available Stock for SKU R7-7800X3D (Requested: 1, Available: 0)`.

## **Scenario C: Idempotency Against Network Fluctuations & Duplicate Submissions**

* **Threat:** Warehouse Wi-Fi drops the HTTP response after the server commits a 50-unit receipt, causing the client to retry the POST request.  
* **Defense Mechanism (`with-idempotency.ts`):**  
  * Client generates `Idempotency-Key: <UUIDv4>` when the Receive form mounts and keeps the same key across retries of that submission.  
  * Server checks `idempotency_keys` table under a unique constraint `UNIQUE(organization_id, idempotency_key)`.  
  * Retried request hits the existing `COMPLETED` key record, verifies the SHA-256 body hash matches, and returns the exact saved `200 OK` JSON payload with `X-Idempotency-Replayed: true` and **zero** duplicate database writes.

# **3.5 CSV Upload Security & Validation Hardening**

* **CSV Injection (Formula Injection) Prevention:**  
  * Malicious CSVs often include cells starting with `=`, `+`, `-`, `@`, `\t`, or `\r` (e.g., `=CMD|' /C calc'!A0`) to execute code when a manager later exports the catalog to Excel.  
  * StockPilot's `csv-import.service.ts` strips or rejects any SKU, product name, category, or supplier field starting with formula control characters during validation preview, and automatically prefixes unsafe strings on CSV export.  
* **Resource Exhaustion & Parser Hardening:**  
  * Enforces max file size of `10 MB` and max `10,000` rows per upload.  
  * Streams CSV parsing and validates every row against strict Zod rules (`sku` regex `^[A-Z0-9-_]{3,64}$`, integer minor units `>= 0`, valid 3-letter ISO currency code, positive integer thresholds).  
  * **Safe Rejection Policy:** Invalid rows never crash the parser or partially corrupt the database. The validation preview returns a deterministic `validation_token` and separates `validRows[]` from `invalidRows[]` (with exact row number, column name, rejected value, and human-readable error message).

# **3.6 PII Handling, Precise Monetary Security & Immutable Audit Trail**

* **PII Minimization & Encryption:**  
  * Supplier contact details (tax IDs, remittance emails, phone numbers) and customer order contacts are scoped strictly to `organization_id` via Row-Level Security (RLS) and redacted in application logs.  
  * Sensitive supplier tax/bank identifiers are encrypted at the application layer using **AES-256-GCM** (`ENCRYPTION_MASTER_KEY`) prior to storage.  
* **Monetary Precision Invariant:**  
  * Every monetary column in the database is stored as `BIGINT` in minor currency units (cents, e.g., `$1,299.99` \-\> `129999`) paired with an explicit `currency CHAR(3)` column (`USD`, `EUR`, `GBP`, `PKR`).  
  * Any currency mismatch between a Purchase Order's header currency and its line item currency is rejected at both the service and DB constraint layers.  
* **Append-Only Forensic Audit Logs & Mandatory Actor/Reason Tracking:**  
  * Every sensitive action (stock adjustment, price change, PO approval, PO receipt, role change, suspicious activity flag) writes to `audit_logs` inside the same database transaction, recording:  
    * `actor_member_id`, `actor_email`, `actor_role`, `ip_address`, `user_agent`, `request_correlation_id`, `action_type`, `entity_type`, `entity_id`, `reason_code`, `reason_notes`, `before_state` (JSONB), and `after_state` (JSONB).  
  * A PostgreSQL `BEFORE UPDATE OR DELETE` trigger on both `audit_logs` and `stock_movements` raises a hard exception (`RAISE EXCEPTION 'Audit logs and stock movements are immutable and append-only'`), guaranteeing tamper-proof forensic integrity even against raw SQL mistakes.
