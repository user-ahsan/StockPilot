## **Step 2: Implement Precise Integer Money & Currency Utility Library**

* **Target Files:**  
  * `src/lib/money.ts`  
  * `tests/unit/money.test.ts`  
* **Implementation Details:**  
  * Build a functional precision money module operating purely on integer minor units (e.g., cents, pence) to prevent floating-point calculation error.  
  * Implement types and error handling:  
    * Custom error class `MoneyPrecisionError` extending `Error`.  
    * Supported ISO 4217 currencies union: `'USD' | 'EUR' | 'GBP' | 'PKR'`.  
      |---|---|  
    * `toCents(amount: number): number`: Multiplies main currency units by 100 and applies `Math.round`. Throws `MoneyPrecisionError` if input is `NaN`, `Infinity`, or non-numeric.  
    * `fromCentsToDisplay(cents: number): string`: Converts integer cents to fixed string format with exactly 2 decimal places.  
    * `formatMoney(cents: number, currency: CurrencyCode): string`: Uses `Intl.NumberFormat` with specified currency code and correct locale formatting.  
    * `calculateLineTotal(quantity: number, unitCostCents: number): number`: Returns integer product of quantity and unit cost. Validates that quantity is an integer `>= 0`.  
    * `calculateTaxCents(subtotalCents: number, taxRateBps: number): number`: Calculates tax using basis points (`1 bps = 0.01%`, `10000 bps = 100%`). Formula: `Math.round((subtotalCents * taxRateBps) / 10000)`.  
    * `calculateMarginBps(costCents: number, priceCents: number): number`: Calculates gross margin percentage in basis points. Formula: `Math.round(((priceCents - costCents) / priceCents) * 10000)`. Returns 0 if `priceCents === 0`.  
* **Acceptance Criteria:**  
  * Unit test suite `tests/unit/money.test.ts` executes 1,000 randomized and edge-case calculations (including zero values, large integer values, non-standard rounding limits) across all supported currencies with zero floating-point precision loss.

## **Step 7: Implement Backend Idempotency Middleware & Client Idempotent Mutation Hook**

* **Target Files:**  
  * `src/server/middleware/with-idempotency.ts`  
  * `src/lib/idempotency-client.ts`  
  * `src/hooks/use-idempotent-mutation.ts`  
  * `tests/idempotency/duplicate-request-replay.test.ts`  
* **Implementation Details:**  
  * Create `withIdempotency` API wrapper inspecting incoming request headers for mandatory `Idempotency-Key` (UUIDv4) on mutation operations (`POST`, `PUT`, `PATCH`).  
  * On request:  
    1. Hash raw request payload body using SHA-256.  
    2. Attempt insertion into `idempotency_keys` table with status `IN_PROGRESS`.  
    3. If unique key constraint violates (key exists):  
       * If status is `IN_PROGRESS`: Return `409 Conflict` with JSON `{ error: "CONCURRENT_REQUEST_IN_PROGRESS" }`.  
       * If status is `COMPLETED`: Verify request body SHA-256 matches stored `request_hash`. If matching, return stored cached payload and response code with header `X-Idempotency-Replayed: true`. If hash differs, return `422 Unprocessable Entity` with `{ error: "IDEMPOTENCY_KEY_PAYLOAD_MISMATCH" }`.  
    4. If key insertion succeeds: Execute target business logic handler inside database transaction. Update `idempotency_keys` record status to `COMPLETED`, storing HTTP response status code and JSON output.  
  * Create frontend React hook `useIdempotentMutation` wrapping `@tanstack/react-query`'s `useMutation`. Generates UUIDv4 key stored in component ref on user interaction intent; reuses same key across network retries until explicit success reset.  
* **Acceptance Criteria:**  
  * Concurrency test `tests/idempotency/duplicate-request-replay.test.ts` fires 5 concurrent HTTP POST requests with identical payload and `Idempotency-Key`. Exactly 1 request executes handler; remaining 4 return cached response payload with `X-Idempotency-Replayed: true`.

# **Phase 5: Central Inventory Ledger Service & Purchase Order Lifecycle**

## **Step 14: Build Central `InventoryLedgerService` (Single Source of Balance Truth)**

* **Target Files:**  
  * `src/server/services/inventory-ledger.service.ts`  
* **Implementation Details:**  
  * Create `InventoryLedgerService`: the **single authoritative service** through which all inventory balance updates must execute.  
  * Implement main transaction method:public static async applyMovement(  
      
      tx: PostgresTransaction,  
      
      params: {  
      
        orgId: string;  
      
        locationId: string;  
      
        variantId: string;  
      
        movementType: MovementType;  
      
        quantityDelta: number; // positive for additions, negative for reductions  
      
        unitCostCents: number;  
      
        referenceType: string;  
      
        referenceId: string;  
      
        actorId: string;  
      
      }  
      
    ): Promise\<{ balanceBefore: number; balanceAfter: number; movementId: string }\>  
      
  * Business rules inside `applyMovement`:  
    1. Lock target balance row via `lockInventoryBalancesForUpdate`.  
    2. Read current `on_hand_qty` and `reserved_qty`.  
    3. Compute `newOnHand = on_hand_qty + quantityDelta` (or calculate dynamic reserved deltas based on `movementType`).  
    4. Assert invariants: `newOnHand >= 0` AND `newOnHand >= reserved_qty`. If violated, throw domain error `InsufficientStockError` or `NegativeBalanceViolationError`.  
    5. Update `inventory_balances` record set: `on_hand_qty = newOnHand`, `version = version + 1`, `updated_at = NOW()`.  
    6. Insert immutable entry into `stock_movements` recording snapshot values (`balance_before`, `balance_after`, `unit_cost_cents`, `quantity_delta`).  
    7. Check if `(newOnHand - reserved_qty) <= reorder_point`. If true, append `LOW_STOCK_ALERT` record to `automation_outbox_events`.  
* **Acceptance Criteria:**  
  * Direct updates to inventory tables outside `InventoryLedgerService` are prohibited by project code structure. Service guarantees atomic ledger logs and balance invariant checks.

* **Implementation Details:**  
  * Implement Sales Order confirmation reservation logic:  
    1. Lock variant rows for update in order via `lockInventoryBalancesForUpdate`.  
    2. Check available inventory: `(on_hand_qty - reserved_qty) >= requested_qty`.  
    3. If sufficient: Update `inventory_balances.reserved_qty = reserved_qty + requested_qty`. Record movement with type `RESERVATION_HOLD`. Set status to `CONFIRMED`.  
    4. If insufficient: Roll back transaction and return `409 Conflict` response (`INSUFFICIENT_AVAILABLE_STOCK`).  
  * Implement Sales Order fulfillment logic:  
    1. Lock target balance rows.  
    2. Atomically decrease both balances:  
       * `on_hand_qty = on_hand_qty - fulfilled_qty`  
       * `reserved_qty = reserved_qty - fulfilled_qty`  
    3. Execute `InventoryLedgerService.applyMovement` with type `SALE_FULFILLMENT` and delta `-fulfilled_qty`. Update status to `FULFILLED`.  
* **Acceptance Criteria:**  
  * Concurrency test `tests/concurrency/concurrent-sales-oversell.test.ts` triggers 5 parallel order requests for 2 available items. Exactly 2 requests succeed in reserving stock; 3 requests are rejected with `409 Conflict`. Zero negative inventory or double allocation occurs.
