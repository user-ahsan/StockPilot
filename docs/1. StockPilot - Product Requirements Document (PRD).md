# **StockPilot — Product Requirements Document (PRD)**

# **Executive Summary & System Foundation**

StockPilot is an enterprise-grade inventory, procurement, and order management platform engineered specifically for modern retail, hardware distribution, and multi-location operations. Unlike legacy point-of-sale overlays or entry-level stock tracking software that rely on naive state overwrites, StockPilot is designed around strict financial accounting principles and ledger-backed transaction processing.

## **Product Purpose**

StockPilot provides multi-location businesses with real-time inventory visibility, strict transactional safety, automated replenishment, and traceable order lifecycles. By modeling every inventory change as an immutable state transition, the platform guarantees absolute auditability across hardware distribution networks, computer retail shops, and multi-warehouse operations.

## **Engineering & Ledger Architecture**

To maintain absolute database integrity under high concurrent loads, StockPilot eliminates raw frontend updates to stock counters. All state alterations execute through server-side ACID transactions.

* **ACID Guarantees:** Every inventory alteration (PO receiving, sales fulfillment, transfer dispatch, or stock adjustment) runs inside isolated database transactions enforcing atomicity, consistency, isolation, and durability.  
* **Pessimistic Row Locking (`SELECT ... FOR UPDATE`):** Race conditions, concurrent checkout oversells, and double-receiving bugs are eliminated at the database driver layer by locking exact `inventory_balances` and `purchase_order_lines` records during write cycles.  
* **Double-Entry Stock Ledger:** Inventory is tracked as an append-only sequence of immutable records in the `stock_movements` table. Current stock balances represent the real-time aggregated snapshot of these immutable entries.  
* **System-Wide Idempotency:** Endpoints processing stock mutations require a client-generated `Idempotency-Key` HTTP header. Duplicate requests caused by network latency or repeated button interactions instantly short-circuit execution and safely replay the original cached response.

## **Granular Role Specifications**

* **OWNER (Organization Super-Admin):**  
  * Manages subscription tiers, organization billing settings, and SSO configurations.  
  * Invites users, revokes access tokens, and assigns organization-wide or location-specific roles.  
  * Creates and decommission physical warehouse and store locations.  
  * Has unrestricted approval authority for high-value purchase orders and stock adjustments.  
* **MANAGER (Store / Operations Manager):**  
  * Oversees daily warehouse operations, product catalog definitions, and unit pricing strategies.  
  * Reviews, approves, or rejects pending Purchase Orders drafted by procurement staff.  
  * Evaluates flagged stock adjustments in the Suspicious Adjustments Queue.  
  * Configures global and location-specific inventory reorder points and automated reorder quantities.  
* **PROCUREMENT\_OFFICER (Buyer / Purchasing Specialist):**  
  * Maintains supplier profiles, preferred vendor lists, and purchasing lead-time configurations.  
  * Drafts POs, attaches line items, verifies tier pricing, and submits orders for Manager review.  
  * Triggers automated dispatch emails/webhooks to suppliers once POs are fully authorized.  
  * Restricted from approving POs above policy thresholds and from altering unit retail prices.  
* **WAREHOUSE\_CLERK (Receiving & Inventory Associate):**  
  * Executes full or partial stock receipts against authorized Purchase Orders.  
  * Submits physical stock adjustment requests (e.g., damaged goods, shrinkage, cycle count adjustments) with mandatory reason codes and documentation notes.  
  * Restricted from viewing financial margin metrics, wholesale markup percentages, or organization valuation reports.  
* **SALES\_ASSOCIATE (POS / Order Desk Staff):**  
  * Queries real-time available inventory across organization storefronts.  
  * Drafts, confirms, and fulfills Sales Orders; locks reservations for pending customer checkouts.  
  * Strictly blocked from overriding retail price quotes without a Manager token and prohibited from modifying stock balances directly.  
* **AUDITOR (Read-Only Compliance & Accounting):**  
  * Accesses historical movement ledgers, system audit logs, and valuation reporting engines.  
  * Generates CSV/PDF compliance reports for external accounting reviews and physical audit reconciliation.  
  * Has zero write permissions across the entire system API.

## **Module A: Inventory Overview Dashboard**

* **KPI Summary Panel:**  
  * *Total Active SKUs:* Quantitative count of active product variants registered in the tenant system, complete with a percentage variance indicator comparing current numbers against the previous 30-day window.  
  * *Total Stock Valuation:* Real-time calculation of monetary capital bound in physical stock, evaluated via `SUM(inventory_balances.on_hand_qty * product_variants.unit_cost_cents)`. Displayed strictly in ISO 4217 standard currency formats (e.g., USD, EUR, GBP) using fixed-point integer math to prevent floating-point rounding errors.  
  * *Low-Stock & Out-of-Stock Status:* Dual-count metrics categorizing items into *Low Stock Status* (`0 < available_qty <= reorder_point`) and *Critical Out-of-Stock Status* (`available_qty == 0`).  
  * *Pending Purchase Orders:* Aggregated monetary value and count of active POs in `SUBMITTED`, `APPROVED`, or `PARTIALLY_RECEIVED` states awaiting warehouse receipt.  
* **Interactive Velocity & Allocation Analytics:**  
  * *Stock Movement Velocity Graph:* Interactive combination chart tracking inbound stock flow (PO receipts, transfer arrivals, positive cycle counts) versus outbound consumption (sales shipments, transfers out, damaged write-offs) over selectable time buckets. Interactive tooltips display date, inbound/outbound units, net delta, top-moving SKU, and monetary impact.  
  * *Valuation by Category & Warehouse Location:* Interactive visual matrix illustrating inventory capital distribution across categories and physical sites. Hovering reveals localized SKU counts, subtotal valuations, and portfolio concentration percentages.  
* **Real-Time Stock Movement Feed:**  
  * Live feed displaying the 25 most recent ledger entries, backed by adaptive polling.  
  * Displays precise timestamps, SKU codes, color-coded movement type tags (`PO_RECEIPT`, `SALE_FULFILLMENT`, `ADJUSTMENT`, `TRANSFER_IN`, `TRANSFER_OUT`), signed delta indicators (`+100`, `-4`), updated balance snapshots, location IDs, and accountable actor tags.  
* **Global Filter Toolbar:**  
  * Location Switcher (`All Locations` or individual branch selection).  
  * Temporal Presets (`Today`, `Last 7 Days`, `Last 30 Days`, `Quarter-to-Date`, `Custom Range`).

* **Step 1 — PO Drafting:** Procurement staff select a supplier, destination warehouse, target delivery date, and currency. Line items are populated with requested quantities and unit cost pricing. System automatically calculates tax subtotals, freight surcharges, line totals, and grand total using integer-cents arithmetic.  
* **Step 2 — Submission:** Order state converts from `DRAFT` to `SUBMITTED`. Line items are locked against unlogged edits, and notification triggers alert designated Managers.  
* **Step 3 — Manager Authorization:** Managers review margin impact, vendor pricing terms, and inventory levels before issuing formal approval (`APPROVED`) or rejection (`REJECTED` with mandatory rejection commentary). Approvals generate vendor-facing PDF outputs and transition status to `ORDERED`.  
* **Step 4 — Atomic Stock Receiving:** Warehouse Clerks enter actual physical quantities received against line items. System executes an atomic transaction that:  
  * Locks PO records and target `inventory_balances` (`SELECT ... FOR UPDATE`).  
  * Enforces upper limits to prevent over-receiving: `received_qty_to_date + incoming_qty <= ordered_qty`.  
  * Appends positive `PO_RECEIPT` entries to `stock_movements`.  
  * Increments `inventory_balances.on_hand_qty`.  
  * Updates PO status to `PARTIALLY_RECEIVED` or `FULLY_RECEIVED`.  
  * Stores `Idempotency-Key` tracking data to prevent duplicate updates.  
* **Step 5 — Complete Transaction Audit Timeline:** Every PO details view renders a chronological audit feed displaying state adjustments, approval signatures, supplier dispatch confirmations, and associated movement IDs.

## **Module D: Sales Order Operations & Fulfillment**

* **Draft & Inventory Reservation:**  
  * When a Sales Associate constructs an order, items are added as draft line items.  
  * Transitioning an order to `CONFIRMED` executes a atomic database check verifying that `available_qty >= requested_qty`.  
  * Upon confirmation, `inventory_balances.reserved_qty` is incremented, immediately reducing `available_qty` (`on_hand - reserved`) across the store layout. This prevents concurrent checkout overselling.  
* **Fulfillment Execution:**  
  * Upon physical packing and dispatch, triggering `FULFILLED` state executes an atomic ledger write.  
  * System decrements `reserved_qty` and `on_hand_qty` simultaneously, records a negative `SALE_FULFILLMENT` movement entry, and issues an invoice receipt statement.  
* **Order Cancellation Handling:**  
  * Canceling an unfulfilled order atomically reduces `reserved_qty` back to zero, making stock available for other orders instantly and logging a clear `SO_CANCELLED` audit trace.

## **Module E: Stock Adjustments & Anomaly Detection**

* **Controlled Adjustment Submissions:** Direct manipulation of current inventory numbers is strictly disabled. Stock adjustments require structured transaction requests detailing location ID, variant SKU, delta (+/-), mandatory reason codes, and notes.  
  * *Standard Reason Codes:* `DAMAGED_IN_TRANSIT`, `WAREHOUSE_BREAKAGE`, `THEFT_SHRINKAGE`, `CYCLE_COUNT_SURPLUS`, `CYCLE_COUNT_DEFICIT`, `WARRANTY_RETURN`.  
  * *Note Rules:* Explanatory notes must meet a minimum length of 15 characters to prevent empty submissions.  
* **Automated Anomaly Detection Rules Engine:**  
  * Adjustments meeting any of the following criteria trigger `flagged_for_review = true` and enter the **Suspicious Adjustments Queue**:  
    * *Value Threshold:* Total monetary impact of write-off exceeds `$500.00 USD` (evaluated via `ABS(delta * unit_cost_cents)`).  
    * *Percentage Variance:* Quantity adjustment exceeds `10%` of the total on-hand inventory for the variant at that location.  
    * *User Velocity Threshold:* Submitting user account has logged 3 or more negative adjustments within a rolling 24-hour window.  
  * Flagged adjustments require explicit review and approval by a Store Manager or Owner before posting to the ledger.

* **Workflow 1 — Low-Stock Notification:** Triggered when `available_qty` falls to or below `reorder_point`. Generates in-app warnings and email digests to designated Store Managers. Notifications are deduplicated to prevent alert spam until stock levels recover.  
* **Workflow 2 — Automated Draft PO Generation:** When stock hits `reorder_point` and no open POs (`DRAFT`, `SUBMITTED`, or `ORDERED`) exist for that SKU at the location, StockPilot generates a draft PO for the primary supplier using pre-configured reorder quantities and submits it to the Manager queue.  
* **Workflow 3 — Supplier Order Dispatch Engine:** Triggered when a Manager approves a PO (`APPROVED` \-\> `ORDERED`). Constructs signed PDF document packages, issues webhooks to vendor endpoints, and dispatches supplier emails. Delivery outcomes are recorded in system execution logs.  
* **Workflow 4 — Daily Sales & Inventory Snapshot Job:** Scheduled cron job executing at store closing (`0 0 * * *`). Aggregates daily gross receipts, COGS, gross margins, total ending stock valuations, and inventory velocity metrics into persistent analytical report snapshots.  
* **Workflow 5 — Suspicious Adjustment Monitoring Engine:** Evaluates every manual adjustment entry against system anomaly rules in real time, routing high-risk entries to the Manager Queue while logging safety checks in audit feeds.

# **Non-Functional Requirements & Security Specifications**

## **Performance & Scalability Targets**

* **API Response Time:** 95th percentile latency below 150ms for mutating ledger transactions under nominal operating load.  
* **Concurrent Transaction Throughput:** Supports up to 500 concurrent checkout write operations per second per tenant without deadlocks or row starvation.  
* **Database Query Efficiency:** All primary inventory operations rely on indexed lookup strategies (`organization_id`, `product_variant_id`, `location_id`), eliminating full table scans.

## **Compliance & Security Baseline**

* **Multi-Tenant Data Isolation:** System-level Row-Level Security (RLS) and API tenant checks enforce strict isolation using `organization_id` on every query, preventing cross-tenant data leaks.  
* **Immutable Audit Trail:** Rows in `stock_movements` and `audit_logs` are protected against updates and deletes at the database driver level.  
* **Security Standards:** API communications enforce TLS 1.3 encryption in transit. Sensitive fields and tenant keys are encrypted at rest using AES-256 techniques. All user logins, password updates, and privilege changes are captured in compliance logs.
