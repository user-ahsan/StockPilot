# **2\. StockPilot — Technical Architecture & Monolithic File Structure Document**

* # **2.1 Architectural Philosophy: Strict Full-Stack Monolith & Zero Config Tampering**

* **Single Deployable Codebase:** StockPilot is architected as a **strict TypeScript Monolith** using **Next.js (Latest App Router)** where the React frontend, REST/RPC Route Handlers, transactional domain services, background automation cron endpoints, database migrations, shared Zod schemas, and AI governance files (`AGENTS.md`, `CLAUDE.md`, `rules.md`) live inside a single unified repository.  
* **Strict `@latest` Version Policy:**  
  * Every framework, library, CLI tool, runtime, and database engine in the stack MUST use the **latest stable version (`@latest`)** resolved at installation time. Hardcoding outdated major/minor version numbers or using deprecated legacy syntax is strictly prohibited.  
* **Immutable Configuration & CLI-Only Styling Mandate:**  
  * **Never Tweak Config Files Manually:** Once initialized via official CLIs (`npx create-next-app@latest`, `npx shadcn@latest init`, `npx shadcn@latest add`), no human or AI agent may manually modify `next.config.ts`, `tsconfig.json`, `postcss.config.mjs`, `components.json`, `eslint.config.mjs`, or `src/app/globals.css`.  
  * **CLI-Only Theme & Component Installation:** The entire visual theme uses the exact [**TweakCN Caffeine Theme**](https://tweakcn.com/editor/theme?theme=caffeine) applied universally via the Shadcn CLI (`npx shadcn@latest add https://tweakcn.com/r/themes/caffeine.json`). Custom CSS rules, inline `style={{}}` color overrides, or manual CSS variable edits are strictly forbidden.

* # **2.2 Precise Technology Stack (All `@latest`)**

* **Runtime & Framework:** Node.js (Latest LTS) \+ Next.js (`@latest`, App Router, TypeScript `@latest` in strict mode).  
* **Frontend UI, Styling & Theme:** React (`@latest`), Tailwind CSS (`@latest`), Shadcn UI (`@latest` via CLI), [**TweakCN Caffeine Theme**](https://tweakcn.com/editor/theme?theme=caffeine) (`npx shadcn@latest add https://tweakcn.com/r/themes/caffeine.json`), Lucide React (`@latest`).  
* **Data Fetching, Caching & Polling:** TanStack Query (`@tanstack/react-query@latest`) with custom adaptive polling hooks, optimistic UI locking, and exponential backoff retry policies.  
* **Data Tables & Charts:** TanStack Table (`@tanstack/react-table@latest`) for dense virtualized catalog grids; Recharts (`recharts@latest`) styled exclusively with Shadcn chart CSS variables (`var(--chart-1)` through `var(--chart-5)`); PapaParse (`papaparse@latest`) for streaming CSV parsing.  
* **Database & ORM:** PostgreSQL (`postgres:latest` on Supabase or Neon) accessed via **Drizzle ORM** (`drizzle-orm@latest` \+ `drizzle-kit@latest`) with explicit `db.transaction()` and `.for('update')` pessimistic row-level locking support.  
* **Authentication & Session Management:** Supabase Auth (`@supabase/ssr@latest` / `@supabase/supabase-js@latest`) or HTTP-only signed JWT session cookies via `jose@latest` integrated with PostgreSQL Row-Level Security (RLS) and application-level RBAC middleware.  
* **Monetary Arithmetic:** `dinero.js@latest` \+ PostgreSQL `BIGINT` minor units (integer cents/paisas) \+ explicit `CHAR(3)` ISO 4217 currency codes. **Floating-point (`FLOAT`, `REAL`, JS `number` decimals) is strictly forbidden for money.**  
* **Testing Suite:** Vitest (`vitest@latest`) for unit & concurrency integration tests, Playwright (`@playwright/test@latest`) for end-to-end multi-actor concurrency & network fluctuation tests.

# **2.4 Frontend-to-Backend Polling & Real-Time Synchronization Architecture**

Because multiple warehouse clerks, buyers, and sales associates operate concurrently across devices, the frontend implements Adaptive Delta Polling via `useAdaptivePolling` \+ `/api/v1/sync/poll`:

* **Lightweight Version Cursor Polling (`/api/v1/sync/poll`):**  
  * Instead of re-fetching massive tables every few seconds, the client polls `GET /api/v1/sync/poll?locationId={id}&sinceVersion={lastLedgerSeq}` every **5,000ms** on active operational screens (PO Receiving, Sales Order POS, Inventory Overview) and every **15,000ms** on catalog/reporting screens.  
  * The endpoint queries the latest `stock_movements.id` sequence, `purchase_orders.updated_at`, and active alert count (sub-5ms indexed lookup).  
  * Only when `serverLedgerSeq > clientLedgerSeq` does TanStack Query invalidate the specific affected query keys (`['inventory-balances']`, `['purchase-order', poId]`, `['overview-kpis']`).  
* **Tab Visibility & Focus Awareness:**  
  * Polling automatically pauses (`refetchIntervalInBackground: false`) when the browser tab is hidden (`document.visibilityState === 'hidden'`) and triggers an immediate delta check upon tab focus (`refetchOnWindowFocus: true`).  
* **Network Fluctuation & Exponential Backoff with Full Jitter:**  
  * If a poll fails due to dropped Wi-Fi or packet loss, the polling interval backs off exponentially: `delay = min(60000, baseInterval * 2^attempt) + random(0, 1000)ms`.  
  * After 2 consecutive failures, the top navigation bar displays an amber **Degraded Network / Reconnecting** indicator showing the exact timestamp of the last verified sync (`Last synced 18s ago`).

# **2.5 Network Fluctuation, Request Deduplication & Idempotency Pipeline**

* **Layer 1 — Frontend Request Deduplication (Read & Write):**  
  * **GET Deduplication:** TanStack Query automatically coalesces concurrent identical `GET` requests mounted by multiple components within the same render cycle into a single network call.  
  * **Mutation Locking & Deterministic Idempotency Key:** When a user opens a mutation form (e.g., *Receive PO Items* or *Submit Stock Adjustment*), `useIdempotentMutation` generates a UUID `idempotencyKey` stored in component state for that specific logical action.  
  * While a request is in flight, the submit button is disabled. If the request times out or fails with a network error (`ECONNRESET`, `502`, `503`, `504`, or browser offline) and the user clicks **"Retry"** (or auto-retry fires), the frontend **reuses the exact same `Idempotency-Key` header**. Only when the mutation succeeds or the user intentionally resets the form is a new key generated.  
* **Layer 2 — Backend Idempotency Middleware (`with-idempotency.ts`):**  
  * Every state-mutating endpoint (`POST`, `PATCH`, `PUT` on PO receipts, sales orders, stock adjustments, CSV commits) requires the `Idempotency-Key` HTTP header (`400 Bad Request` if missing).  
  * The middleware computes a SHA-256 hash of `(organization_id, user_id, method, path, raw_body)`.  
  * It executes an atomic upsert into the `idempotency_keys` table:  
    * **Case A (New Key):** Inserts status `IN_PROGRESS` with `locked_until = NOW() + INTERVAL '30 seconds'`, executes the transactional handler, stores `response_status` and `response_body`, and marks status `COMPLETED`.  
    * **Case B (Duplicate Key \+ `COMPLETED`):** Verifies the request payload hash matches (returns `422 Unprocessable Entity` if a client reused an `Idempotency-Key` with different payload data), then immediately returns the cached `response_status` and `response_body` with header `X-Idempotency-Replayed: true`.  
    * **Case C (Concurrent Duplicate Key \+ `IN_PROGRESS`):** If two identical packets arrive 10ms apart due to a proxy retry, the second request receives `409 Conflict (Request Already In Progress — Retry After 2s)` without touching business tables.  
* **Layer 3 — Database Deduplication & Pessimistic Locking:**  
  * Unique composite constraints (`UNIQUE(organization_id, sku)`, `UNIQUE(organization_id, location_id, variant_id)` on `inventory_balances`, `UNIQUE(organization_id, idempotency_key)` on `stock_movements`) guarantee that even if application middleware were bypassed, PostgreSQL rejects duplicate ledger mutations at the storage engine level.  
  * Deterministic lock ordering (`ORDER BY product_variant_id ASC` before `SELECT ... FOR UPDATE`) prevents database deadlocks when two concurrent orders contain the same items in reverse order.

# **2.6 Infrastructure, Hosting & Database Connection Topology**

* **Application Compute:** Deployed as a monolithic Next.js container/serverless deployment (Vercel Pro or Dockerized Node.js on Railway/AWS ECS) in the same cloud region (`us-east-1` or `ap-south-1`) as the primary PostgreSQL database to keep round-trip query latency under 2ms.  
* **Database Connection Pooling:**  
  * **Pooled Application Traffic (`DATABASE_URL`):** Connects through PgBouncer / Supabase Supavisor in **Transaction Mode** (port `6543`) to support hundreds of concurrent HTTP requests without exhausting PostgreSQL connections.  
  * **Direct Migration & Advisory Lock Traffic (`DIRECT_DATABASE_URL`):** Connects directly to PostgreSQL (port `5432`) for Drizzle schema migrations and long-running administrative tasks.  
* **Transactional Outbox Pattern for Automation:**  
  * Instead of firing third-party supplier emails or Slack alerts inside the middle of a database transaction (which would hold row locks open during slow HTTP calls), the database transaction inserts a row into `automation_outbox_events` inside the same `COMMIT`.  
  * The monolithic worker route (`/api/internal/cron/outbox-processor`, triggered every 30s or immediately via non-blocking background hook) polls `SELECT * FROM automation_outbox_events WHERE status = 'PENDING' FOR UPDATE SKIP LOCKED LIMIT 50`, dispatches emails/alerts idempotently, and marks them `PROCESSED`.
