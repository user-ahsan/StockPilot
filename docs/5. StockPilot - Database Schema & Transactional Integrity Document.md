# 5\. StockPilot — Database Schema & Transactional Integrity Document

This document defines the underlying relational database architecture, structural integrity rules, enumerated types, table specifications, and strict transactional blueprints governing the StockPilot Inventory and Order Management System.

# 5.1 Core Database Engineering Rules

* **Target RDBMS & Isolation Standards:**  
  * Engine: PostgreSQL (Latest Stable Release, `postgres:latest`) running with strict ACID guarantees. All Drizzle ORM and database tooling packages must specify using the latest (`@latest`) version without hardcoded version numbers.  
  * Default Transaction Isolation Level: `READ COMMITTED` combined with explicit pessimistic row-level locking (`SELECT ... FOR UPDATE`) executed in deterministic order to prevent deadlocks during concurrent multi-item stock modifications.  
  * Foreign Key Constraint Enforcement: `ON DELETE RESTRICT` is explicitly declared on all transactional foreign keys to prevent orphan ledger entries, orphaned PO/SO line items, or silent physical stock balance deletion.  
* **Monetary Storage & Multi-Currency Rules:**  
  * Zero Floating-Point Currency: Floating-point types (`FLOAT`, `DOUBLE PRECISION`, `NUMERIC` without fixed scaling) are strictly prohibited for monetary values.  
  * Storage Format: All financial amounts are stored as 64-bit integers (`BIGINT`) representing minor currency units (e.g., integer cents, paisas, or yen).  
  * Explicit Currency Tagging: Every table containing monetary amounts MUST maintain an accompanying `CHAR(3)` ISO 4217 code column validated via regex check constraints: `CHECK (currency ~ '^[A-Z]{3}$')`.  
* **Anti-Duplication & Ledger Integrity Rules:**  
  * Immutable Audit Ledger Verification: Every physical inventory state represented in `inventory_balances` MUST strictly equal the aggregate mathematical sum of all historical `stock_movements.quantity_delta` associated with the exact `(organization_id, location_id, product_variant_id)` triplet.  
  * Single-Service Mutation Boundary: Direct `UPDATE` or `DELETE` SQL operations on `inventory_balances` outside of the unified `inventory-ledger.service.ts` transaction orchestrator are prohibited at the application layer.  
  * Constraint-Level Uniqueness Enforcements: Composite `UNIQUE` indexes enforce zero-duplication policies across multi-tenant domains, including duplicate SKUs, duplicate location balance tracking, duplicate line items per purchase/sales order, and duplicate idempotency processing keys.

## Blueprint 1: Atomic, Row-Locked Purchase Order Stock Receipt

The following SQL transaction demonstrates how StockPilot processes stock receipt against a Purchase Order. It executes pessimistic locking in deterministic order, verifies allocation constraints, appends immutable ledger records, updates balances, and updates the aggregate PO state.BEGIN;

\-- 1\. Lock the Purchase Order header row to serialize concurrent clerks on this PO

SELECT id, status, location\_id, currency

FROM purchase\_orders

WHERE id \= 'a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11'::uuid 

  AND organization\_id \= '11111111-1111-1111-1111-111111111111'::uuid

FOR UPDATE;

\-- Application logic verifies: status IN ('ORDERED', 'PARTIALLY\_RECEIVED'); 

\-- If invalid, issue ROLLBACK and abort with HTTP 409 Conflict.

\-- 2\. Lock PO line items in deterministic product\_variant\_id ASC order to eliminate deadlock risks

SELECT id, product\_variant\_id, ordered\_qty, received\_qty, unit\_cost\_cents

FROM purchase\_order\_items

WHERE purchase\_order\_id \= 'a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11'::uuid 

  AND organization\_id \= '11111111-1111-1111-1111-111111111111'::uuid

ORDER BY product\_variant\_id ASC

FOR UPDATE;

\-- Application logic validates: (received\_qty \+ incoming\_qty \<= ordered\_qty) for each item.

\-- 3\. Ensure target inventory\_balances rows exist (upsert zero row if first receipt at location)

INSERT INTO inventory\_balances (

  organization\_id, location\_id, product\_variant\_id, on\_hand\_qty, reserved\_qty

)

VALUES 

  ('11111111-1111-1111-1111-111111111111'::uuid, '22222222-2222-2222-2222-222222222222'::uuid, '33333333-3333-3333-3333-333333333333'::uuid, 0, 0\)

ON CONFLICT (organization\_id, location\_id, product\_variant\_id) DO NOTHING;

\-- Lock inventory balances in matching deterministic order

SELECT id, product\_variant\_id, on\_hand\_qty, reserved\_qty

FROM inventory\_balances

WHERE organization\_id \= '11111111-1111-1111-1111-111111111111'::uuid 

  AND location\_id \= '22222222-2222-2222-2222-222222222222'::uuid 

  AND product\_variant\_id IN ('33333333-3333-3333-3333-333333333333'::uuid)

ORDER BY product\_variant\_id ASC

FOR UPDATE;

\-- 4\. Increment purchase\_order\_items received\_qty

UPDATE purchase\_order\_items

SET received\_qty \= received\_qty \+ 10

WHERE id \= '44444444-4444-4444-4444-444444444444'::uuid 

  AND (received\_qty \+ 10\) \<= ordered\_qty;

## Blueprint 2: Immutability Trigger Enforcement on `stock_movements` and `audit_logs`

To strictly guarantee ledger append-only immutability, database-level PL/pgSQL triggers block any attempted `UPDATE` or `DELETE` operations at the engine level regardless of database user privilege grants.l  
CREATE OR REPLACE FUNCTION prevent\_ledger\_mutation()  
RETURNS TRIGGER AS \$\$  
BEGIN  
RAISE EXCEPTION 'Table % is strictly append-only. UPDATE and DELETE operations are prohibited.', TG\_TABLE\_NAME  
USING ERRCODE \= 'RESTRICT\_VIOLATION',  
HINT \= 'Ledger records must remain permanent for audit compliance.';  
END;  
\$\$ LANGUAGE plpgsql;

CREATE TRIGGER trg\_immutable\_stock\_movements  
BEFORE UPDATE OR DELETE ON stock\_movements  
FOR EACH ROW EXECUTE FUNCTION prevent\_ledger\_mutation();

CREATE TRIGGER trg\_immutable\_audit\_logs  
BEFORE UPDATE OR DELETE ON audit\_logs  
FOR EACH ROW EXECUTE FUNCTION prevent\_ledger\_mutation();
